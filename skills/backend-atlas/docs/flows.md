# 流程：业务循环「怎么跑」

backend-atlas 的流程页与 agent 整理流程的做法。build 报「草稿 N」、锚点对不上、或用户问「这个循环怎么跑」时读。

## 流程：业务循环「怎么跑」（agent 整理，锚点保真）

图回答「谁调谁」，流程回答「这个循环怎么跑」：哪里是循环、哪里分岔、什么条件下停、停成什么结局、什么时候交给后台。

**分两层，机器做确定的，agent 做判断的**：

1. **事实（自动，零 LLM）**：抽取器从每个入口（HTTP / Hub / 后台服务）和每个被 `Task.Run` 带到后台的方法出一棵控制流骨架——
   循环、if 分岔、护栏（if 里直接 throw / return）、结局原话（`throw AppException(409, "该邮箱已注册")` → 409 · 该邮箱已注册）、catch、交给后台（→ 另一条流程）。
   仓库内调用内联 4 层；步骤名取方法头紧贴的 `[ … ]` 注释（冒号前）；推送事件名取调用点实参；只往下调、不读写的小帮手剪掉。
   每个节点带**锚点键** `方法 › 种类:关键文本`（例 `TurnRunner.Loop›guard:turn.ModelCalls >= MaxModelCalls`）：挪行号不变，改了那条语句才失效。
2. **整理（agent）**：没整理的流程自动出**草稿**（只留护栏 / 结局 / 分岔 / 循环 / 写推外呼的步骤，按循环切阶段）。关键流程由 agent 写进语义层 `flows`：
   分几个阶段、每步的人话名、哪一支是主路、结局的语气。**step / guard / branch / side 必须 `"at"` 引用锚点键**（前端步骤 `l:"ui"` 除外），build 逐个核对——
   agent 编不出代码里没有的步骤；代码改了、锚点对不上，build 直接报「哪条流程的哪个节点」，只重整那几条。

**agent 怎么整理一条**（build 每次都打印 `流程 N 条 · 已整理 M · 草稿 K · 大纲 <WORK>/flows/index.md`）：

1. 挑值得整理的：带循环、会交给后台、分支多的（简单增删改查看草稿就够）。
2. 先读 `<WORK>/flows/index.md`（一行一条，草稿按复杂度排，越靠前越值得整理），再**只读那一条**的文件看它的事实树：每行 `[种类] 文本 ‹锚点键› 文件:行`；需要时再读源码补语义。别把整个 flows/ 读进来。
3. 写进语义层（项目的 `atlas.json`）的 `flows`，键用流程 id、`"动词 路由"` 或 `"类.方法"`：

```json
"flows": { "TurnRunner.Run": { "name": "Agent 轮次", "story": "一句话讲它怎么跑",
  "tree": [ { "t": "每一步", "loop": "最多 60 次 · 30 分钟", "at": "TurnRunner.Loop›loop:true", "kids": [
      { "k": "guard", "t": "调用满 60 次？", "at": "TurnRunner.Loop›guard:turn.ModelCalls >= MaxModelCalls",
        "kids": [ { "k": "exit", "t": "限额", "why": "调用满 60 次", "tone": "warn" } ] },
      { "t": "取插话", "at": "TurnRunner.Loop›call:TurnRunner.DrainInterjections" },
      { "k": "branch", "t": "模型怎么收尾？", "at": "…", "kids": [ { "k": "case", "t": "调了工具", "main": true, "kids": [] } ] },
      { "k": "back", "t": "下一步", "to": "TurnRunner.Loop›call:TurnRunner.DrainInterjections" } ] } ] } }
```

   顶层每项是一个阶段（`loop` = 循环段，`inLoop` = 也在循环里）；`k` ∈ step / guard / branch / case（`main` = 主路）/ exit（`tone` ∈ ok / wait / warn / fail / stop）/ back（`to` = 目标的锚点键）/ link（`flow` = 另一条流程 id）/ tool / side；
   `l` = 执行者（ui / svc / bg / model / tool），泳道按它分行；读写推送由锚点自动带出（方法自己的 + 它直接调到的下一层），可用 `r` 补（`w:表` `p:事件` `h:外部`）。
4. 重跑 build，直到不报锚点错；打开流程页看一眼。

**在哪看**：域抽屉里「怎么跑」一节（后台流程——Agent 轮次、生成 worker——只能从这里进）· 循环抽屉「展开成流程图」· 流程页里点「跳到另一条流程」的节点直达。
流程页盖在系统图上：问题页签选画法（怎么走 逻辑树 / 谁来做 泳道 / 怎么绕 环形跑道），**默认按形态自动选**（有回环 → 跑道；跨 ≥3 个执行者 → 泳道；其余 → 逻辑树；草稿一律先逻辑树、深处折叠），
右栏先是 **IBO**——I 输入（入口路由 · 前端触发 · 带着的请求字段〈抽取器把 …Dto / Input / Body / Request / Command 展开成字段〉· 读哪些表）→ B 经过（阶段主干，循环段标 ↺ · 外部 · 工具）→ O 输出（写表 · 推送 · 结果〈完成 / 等用户〉· 转交到哪条流程），全部从流程树汇总；
下面常驻「为什么停」（结局倒推）；流程图不做悬停聚焦（太闪），节点上是默认光标、空白处才是抓手；打开时自动缩到看得到全图（最小 0.5），拖动平移、⌘ + 滚轮缩放、「适应全图 / 100%」；环形跑道站点只写名字、站下只挂终点，细节在悬停提示；悬停亮来路去路，⌘ 点节点开源码，Esc 回系统图。
抽屉里「业务逻辑怎么跑」紧跟数字那一排，主按钮直达最值得看的一条（整理过的优先）。画法定稿在 `docs/lab/loop-mindmap.html`（对照版两轮），`viewer/flow.js` / `flow.css` 从它抽出，改画法先改对照页。

**成本（实测，中型 / 大型项目）**：流程抽取 1.0 / 1.5 秒（服务端抽取合计约 5 / 7 秒）；一张流程图渲染真实流程 < 3ms，1000 节点 ≈ 40ms（`docs/lab` 里 `__bench()` 可复测）。
