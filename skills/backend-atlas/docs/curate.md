# 整理：按业务归类、起名、让图好读

第一次接项目（build 生成了骨架）、`.atlas/index.md`「还差什么」里有整理项、或用户说图看不懂时读。

骨架只会按控制器分域，用「动词 路由」当循环名，能看，但说的不是业务话。**整理由 agent 负责**：把抽取出来的事实归纳成人看得懂的业务图。
整理只写进 `atlas.json`。事实每次重跑都从代码重抽，两边互不覆盖，所以整理过的东西不会被自动更新冲掉。

## 初次整理（一次做完）

1. 跑一趟 `run.sh`，`SEM` 指向还不存在的 `atlas.json`，会生成骨架和 `.atlas/`。
2. 只读 `.atlas/curate.md`，不用开源码。开头写了本项目有没有 CONTEXT.md、有几条 ADR。每个域列了端点、写了哪些表、相关 ADR；每条没起名的循环和流程列了方法注释、写表、推送、前端入口等；最后是图上不好读的地方。
   只有这些还判断不了归属（比如两个控制器是不是同一块业务）时，才去读那几个文件。
3. 取名的材料按这个顺序找：
   1. 项目的 `CONTEXT.md`（统一语言）
   2. ADR 标题
   3. 代码注释
   4. 路由

   都没有的业务说法不要发明，拿不准的问用户。纯技术端点（健康检查、登录、上传）直接用通用说法。
4. 写进 `atlas.json`，从粗到细：
   - **域**：按业务归类，同一块业务的 `S:c:控制器` 放进同一个域的 `match`。起业务名（「订单」，不是「OrdersController」），写一句 `desc` 说它管什么。
     后台任务、服务文件属于某块业务的，在那个域的 `match` 里点名它的叶子 `S:f:<相对路径>`（叶子只能精确点名）；没点名的，按「谁在用」自动归位。
     域 id 可以改：`groups`、`edgeLabels` 里引用它的地方对不上，build 会报出来。
   - **分组**：域里直接挂的卡超过 8 张，就用 `groups` 按功能分组（漏一张 build 会报出来）。
   - **循环**：`loops` 里 `"POST /x": ["人话名", "一句话：谁在什么时候做什么，落到哪"]`。
   - **流程**：GET 查询和后台流程先只起名 `"流程 id": { "name", "story" }`。值得细讲的（带循环、交给后台、分支多）再按 `docs/flows.md` 写 `tree`。
   - **连线**：域与域之间线多的，用 `edgeLabels` 写一句业务话（「发消息时扣积分」）。
5. 重跑，按报错补（没认领 / 没分组 / 键对不上），直到 curate.md 里剩下的确实不值得整理。
6. 出图 `open` 给用户看，请用户挑出不对的名字和分法。

「还差什么」里的**体检项**（跨域直调、多域共写……）是代码层面的问题，整理消不掉：要么改代码，要么在 ADR 里写清为什么接受。

## 以后：顺路整理

- **新增端点**会自动落进它的控制器所在的域；没名字时用「动词 路由」，并出现在 curate.md 里，顺手起名。
- **新控制器、或者没被认领的新文件**会让 build 报错，按报错归进业务域就行。这是有意的：没想清楚归属的东西，不该悄悄混进图里。
- **路由改了**：旧名字的键对不上会报错，把键挪过去即可。
- 改到哪个域，就顺手清掉那个域在 curate.md 里的项。不用专门开一次大扫除。
- **ADR 也一起整理**：「还差什么」里有「可以删的 ADR」时，列给用户确认后删；同一件事被一串 ADR 反复修订的，合并成一条新的。做法见 `docs/adr.md`「清理」。
